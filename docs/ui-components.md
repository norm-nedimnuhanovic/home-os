# UI Components & Styling

How shared UI is organized, styled, and extended in Home OS: where a
component lives, how a new shadcn/ui primitive gets added, the Tailwind
design-token setup every module's components draw from, and why there is no
Storybook in V1. This doc governs *presentation*; it doesn't re-litigate
*what* a screen shows (`plan.md`), *where its data comes from*
(`docs/access-control.md`'s `visibility`/`ObjectShare` contract,
`src/modules/<key>/queries/`), or *how a mutation is wired*
(`docs/forms.md` — not yet written; if a task needs it, write it following
this doc's shape before proceeding, per `CLAUDE.md`'s gap-filling rule).

**Companion docs, not duplicated here:**
- [`docs/project-structure.md`](./project-structure.md) §8 is the authority
  on *where UI files live* — this doc goes one level deeper on *how they're
  built and styled*. If the two ever disagree on a file path,
  `project-structure.md` wins (it says so explicitly).
- [`docs/resources.md`](./resources.md) §2.7–2.9 is the fullest worked
  example of a module's UI end to end (`Contact`'s list view, detail view,
  and form) — several patterns below are named references back to it rather
  than re-paraphrased.
- [`docs/access-control.md`](./access-control.md) owns *what a component is
  allowed to render* (visibility-scoped query results, role-gated buttons)
  — this doc only covers presentation once that data has already been
  correctly scoped.
- `docs/forms.md` / `docs/testing.md` — referenced below where relevant;
  both are harness gaps as of this writing (not yet written). Don't invent
  their conventions here; write them, following this doc's tone, the first
  time a task actually needs one.

## 1. Stack recap (locked — don't re-litigate)

| Layer | Choice |
|---|---|
| CSS | Tailwind CSS |
| Component primitives | shadcn/ui — Radix UI primitives (`--base radix`), **copied into the repo**; the underlying `radix-ui` package is a real dependency, but there's no `shadcn` package itself |
| Icons | [`lucide-react`](https://lucide.dev) — shadcn's own default icon set; already the icon library in the one committed UI example (`docs/resources.md`'s `contact-list.tsx` imports `Star` from `lucide-react`) |
| Forms | `react-hook-form` + `zod` + shadcn's `Form`/`FormField` wrapper components (§9) |
| Component docs | **No Storybook in V1** (§13) |
| Dark mode | Tokens are structurally in place from `shadcn init` (§5); no user-facing theme toggle ships in V1 — `plan.md` never calls for one |

Nothing here is a per-module decision — every module's `components/` folder
draws from the same Tailwind config and the same `src/components/ui/`
primitives. A module never ships its own copy of `button.tsx` or its own
color palette.

## 2. The three tiers of shared UI

Per `docs/project-structure.md` §8, every component in the app belongs to
exactly one of three tiers. Knowing which tier a component is in tells you
where its file goes and who's allowed to import it.

| Tier | Location | Contains | Import from other modules? |
|---|---|---|---|
| **Primitives** | `src/components/ui/` | shadcn/ui components as generated by the CLI (`button.tsx`, `dialog.tsx`, `table.tsx`, `select.tsx`, `form.tsx`, `card.tsx`, `switch.tsx`, `dropdown-menu.tsx`, …) | Yes, by every module and by `src/app/` — this is the shared vocabulary |
| **Cross-module composites** | `src/components/` (no `/ui`) | Generic, domain-agnostic pieces with no entity of their own: `app-shell/nav.tsx` (one responsive nav, not separate sidebar/navbar files), `app-shell/command-palette.tsx`, `page-header.tsx`, `empty-state.tsx`, `confirm-dialog.tsx` | Yes, by every module — but a composite never imports a specific module's barrel; it takes props |
| **Module-specific** | `src/modules/<key>/components/` | Anything with domain meaning: `task-card.tsx`, `kanban-column.tsx`, `contact-list.tsx`, `budget-progress.tsx`, `transaction-form.tsx` | No — per `docs/project-structure.md` §7's import-boundary rule, another module reaches a component only via `src/app/` composing pages, never `@/modules/<other>/components/*` directly |

One exception, carried over unchanged from `docs/project-structure.md` §8:
platform-substrate entities that live in `src/lib/` (not `src/modules/`)
keep their components next to their own entity, not in generic
`src/components/`, because they have real domain meaning even though
they're platform code — e.g. `src/lib/notifications/components/
notification-bell.tsx`, `src/lib/household/components/{member-list.tsx,
invite-form.tsx}`, `src/lib/module-registry/components/
module-grant-review.tsx`. Same rule as tier 3, different owning layer.

**Known harness inconsistency to ignore:** `AGENTS.md`'s older folder sketch
places shadcn primitives under `src/shared/components/ui/`. That predates
`docs/project-structure.md`'s reconciled tree and its "the code that isn't
inside `src/modules/` and isn't `src/lib/` lives in `src/components/`" rule.
Follow `src/components/ui/` (this doc, `docs/project-structure.md`,
`docs/resources.md` all agree); `AGENTS.md`'s tree gets fixed to match the
next time it's touched, per the same reconciliation pattern
`docs/orm-conventions.md` and `docs/resources.md` already use for their own
drift notes.

## 3. Reuse before you build

Before writing a new component, check — in this order — whether one
already covers the need:

| Need | Check first | Don't build |
|---|---|---|
| A button, input, select, dialog, dropdown, badge, card, table, tabs, tooltip, etc. | `ls src/components/ui/` — if it's not there, §4 adds it in one command, it isn't hand-rolled | A bespoke styled `<button>`/`<div>` reimplementing what Radix + shadcn already solved (focus trapping, ARIA roles, keyboard nav) |
| A page header, empty list state, "are you sure?" confirmation, the nav/sidebar/command palette shell | `src/components/` | A copy of `page-header.tsx` pasted into one module's `components/` folder |
| A list/card/form for a specific entity (`TaskCard`, `RenewalCard`, `BudgetProgress`) | That module's own `src/modules/<key>/components/` — check whether a sibling entity's component (e.g. `contact-card.tsx` next to the `Contact` you're building `Renewal` alongside) already has 90% of the shape you need | A generic `<EntityCard>` abstraction that tries to cover every module's entity through props-driven polymorphism — per `docs/access-control.md`/`AGENTS.md`'s general anti-pattern stance, prefer one obvious component per entity over one clever one for all of them |
| A "shared with…" / visibility picker for a `private \| household \| specific_members` field | Check `src/lib/household/components/` for a shared `<ObjectSharePicker>`/member-picker before writing a second one — every entity with a `visibility` column (`Task`, `Note`, `Event`, `KanbanBoard`, `Transaction`, `Document`, `Renewal`, `Contact`, `ShoppingList`) needs the exact same UI shape, so this is exactly the kind of "build once, reuse everywhere" case `AGENTS.md`'s Step 0 reuse table calls out for the *data* layer — the same logic applies to the *UI* layer | A per-module visibility `<Select>` hand-wired against that module's own enum values |
| An icon | `lucide-react`'s existing set | A custom SVG/icon font for something Lucide already has |

If the answer really is "nothing existing covers this," build it in the
correct tier from §2 — don't default to module-specific just because that's
the fastest place to drop a new file.

## 4. Adding or updating a shadcn/ui primitive

Primitives are **copied into the repo and committed**, not installed as a
versioned dependency — there's no `shadcn` package in `package.json`'s
`dependencies`, only the underlying Radix UI package (`radix-ui`) that the
copied component code imports.

### 4.1 One-time init (Phase 0 — already in `ROADMAP.md`'s checklist)

```bash
pnpm dlx shadcn@latest init --base radix
```

`--base radix` is a locked, one-time choice (`docs/ui-components.md`'s own
history: the CLI's default is now Base UI, not Radix; this repo pins to
Radix — see `pnpm-workspace.yaml`'s `overrides` section for a related
Radix-specific pin). This generates `components.json` at the repo root and
the first primitives. Commit the generated file as-is except for the
`aliases` block, which must match `docs/project-structure.md`'s actual
layout, not the CLI's defaults:

```json
// components.json
{
  "$schema": "https://ui.shadcn.com/schema.json",
  "style": "radix-nova",
  "rsc": true,
  "tsx": true,
  "tailwind": {
    "config": "",
    "css": "src/app/globals.css",
    "baseColor": "neutral",
    "cssVariables": true,
    "prefix": ""
  },
  "iconLibrary": "lucide",
  "rtl": false,
  "aliases": {
    "components": "@/components",
    "utils": "@/lib/utils",
    "ui": "@/components/ui",
    "lib": "@/lib",
    "hooks": "@/hooks"
  },
  "menuColor": "default",
  "menuAccent": "subtle",
  "registries": {}
}
```

`tailwind.config: ""` is correct, not a mistake to "fix" — this stack is on
Tailwind v4, which is configured via `@theme` in CSS (§5.1), not a
`tailwind.config.ts` file. `style: "radix-nova"` and `baseColor: "neutral"`
are one-time locked choices (picked for a dense, information-heavy
household-admin app rather than a marketing site) — don't re-run `init`
with different values later; a per-component style drift is exactly the
inconsistency Storybook would otherwise exist to catch (§13). `hooks:
"@/hooks"` is included because a few shadcn components (e.g. `sonner`/toast)
generate a hook file the CLI expects to place under `src/hooks/` — that
folder doesn't exist yet in `docs/project-structure.md`'s tree because
nothing has needed it yet; create it the first time a component's CLI
output requires it, same as any other "add the folder when the first file
needs it" case in this repo.

### 4.2 Adding a new primitive

```bash
pnpm dlx shadcn@latest add button dialog table dropdown-menu
```

Each component lands as a plain `.tsx` file under `src/components/ui/`
(e.g. `src/components/ui/dropdown-menu.tsx`) — inspect the diff like any
other generated code before committing it, same as a Prisma migration.
Because it's copied in, **you own it**: customizing a primitive's default
styling (e.g. tightening `Card`'s default padding, adding a `KanbanBoard`
column-drag affordance to `Card`'s hover state) is a normal edit to that
file, not a fork you need to keep in sync with upstream. There is no
`shadcn upgrade` command to run later that would silently overwrite a local
customization — re-running `add <component>` on a component you've already
customized will prompt to overwrite, so don't re-run it carelessly once a
primitive has diverged from its generated defaults.

### 4.3 What never goes in `src/components/ui/`

Nothing with a `@prisma/client` import, nothing that calls a Server Action,
nothing that knows what a `Task` or a `Household` is. A primitive takes
`className`, `variant`, `children`, and other generic props only — domain
logic lives one tier up (§2).

## 5. Tailwind configuration & design tokens

### 5.1 Config file

This stack is on **Tailwind v4**, which has no `tailwind.config.ts` — there
is no such file in this repo, and adding one is not a "fix" for anything.
Configuration is CSS-first: `postcss.config.mjs` wires in the
`@tailwindcss/postcss` plugin, and `src/app/globals.css` does the rest via
`@import`/`@theme`/`@custom-variant`:

```css
/* src/app/globals.css (excerpt) */
@import "tailwindcss";
@import "tw-animate-css";        /* the v4-native replacement for the old tailwindcss-animate plugin */
@import "shadcn/tailwind.css";

@custom-variant dark (&:is(.dark *));

@theme inline {
  --color-background: var(--background);
  --color-foreground: var(--foreground);
  --color-primary: var(--primary);
  --color-primary-foreground: var(--primary-foreground);
  /* …one @theme entry per design token, mapping a Tailwind utility name
     (--color-*, --radius-*) to the actual CSS variable defined in :root/.dark
     below — this is what makes `bg-primary`/`rounded-lg`/etc. resolve. */
  --radius-lg: var(--radius);
}
```

`@custom-variant dark (&:is(.dark *))` is the v4 equivalent of Tailwind v3's
`darkMode: ["class"]` — it means dark mode activates by a `.dark` class on
`<html>`, not the OS-level `prefers-color-scheme` alone. **In V1, that class
is never toggled** — there is no theme switcher in the nav (`plan.md` names
no such feature), so the app renders in the light-mode token values only.
The `.dark { ... }` block in `globals.css` (§5.2) exists purely so a future
`next-themes`-driven toggle is a small, additive change (wire the provider +
one nav button) rather than a design-token rewrite — don't build that
toggle preemptively; wait for a task that asks for it.

### 5.2 Design tokens (`src/app/globals.css`)

Every color a component uses (`bg-background`, `text-muted-foreground`,
`border-input`, …) is a CSS custom property in `oklch(...)`, not a literal
Tailwind palette color like `slate-500` — this is what makes a future theme
change (or dark mode activation) a token edit instead of a find-and-replace
across every component:

```css
/* src/app/globals.css (excerpt) */
:root {
  --background: oklch(1 0 0);
  --foreground: oklch(0.145 0 0);
  --primary: oklch(0.205 0 0);
  --primary-foreground: oklch(0.985 0 0);
  --destructive: oklch(0.577 0.245 27.325);
  --border: oklch(0.922 0 0);
  --radius: 0.625rem;
  /* …one entry per token — see the file itself for the full set (card,
     popover, secondary, muted, accent, chart-1..5, sidebar-*). */
}

.dark {
  --background: oklch(0.145 0 0);
  --foreground: oklch(0.985 0 0);
  --primary: oklch(0.922 0 0);
  --primary-foreground: oklch(0.205 0 0);
  --destructive: oklch(0.704 0.191 22.216);
  --border: oklch(1 0 0 / 10%);
  /* mirrors every :root token above with its dark-mode value */
}

@layer base {
  * { @apply border-border outline-ring/50; }
  body { @apply bg-background text-foreground; }
  html { @apply font-sans; }
}
```

These are the values `shadcn init` generates for the `neutral` base color
(§4.1) — copy them verbatim from the CLI's output rather than retyping by
hand, and don't hand-tune individual token values per module; a module that
needs a visually distinct accent (e.g. Finance's "overdue" state, a
`Renewal` in `expired` status) uses semantic *variant* classes on top of
these tokens (`destructive`, `muted`), never a one-off hex value baked into
a component (see §6 for the one place raw, non-token colors legitimately
appear).

### 5.3 `cn()` — the one class-merging helper

```ts
// src/lib/utils.ts
import { clsx, type ClassValue } from "clsx";
import { twMerge } from "tailwind-merge";

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs));
}
```

Every component that conditionally applies classes uses `cn()` — never
manual template-literal string concatenation for conditional classes,
since `twMerge` is what correctly resolves conflicting Tailwind classes
(e.g. a caller passing `className="p-2"` into a component whose own
default is `p-4` — plain concatenation would apply both and let CSS
source-order decide by accident; `cn()` keeps the last one deterministically):

```tsx
// src/modules/tasks/components/task-card.tsx (excerpt)
<div className={cn("rounded-lg border p-4", isOverdue && "border-destructive", className)}>
```

## 6. Enum-driven colors vs. free-text, per-row colors

Home OS has two genuinely different kinds of "color" in the data model, and
they need two different rendering techniques. Conflating them is a real
bug class in a Tailwind app, not a style nitpick.

### 6.1 Enum-driven — a static lookup map, plain Tailwind classes

`Task.priority` (`low | medium | high | urgent`), `KanbanColumn.columnType`
(`todo | in_progress | done | custom`), `Renewal.status`
(`active | expiring_soon | expired | renewed | cancelled`), and similar
fixed enums have a **known, closed set of values** — write the mapping as a
plain object with literal Tailwind class strings so Tailwind's compiler can
see every class name at build time:

```ts
// src/modules/tasks/entities/task.ts
import type { TaskPriority } from "@prisma/client";

export const TASK_PRIORITY_BADGE_CLASSES: Record<TaskPriority, string> = {
  low: "bg-muted text-muted-foreground",
  medium: "bg-secondary text-secondary-foreground",
  high: "bg-accent text-accent-foreground",
  urgent: "bg-destructive text-destructive-foreground",
};
```

```tsx
<Badge className={TASK_PRIORITY_BADGE_CLASSES[task.priority]}>{task.priority}</Badge>
```

This works because every class string is written literally, somewhere in
source, for Tailwind's content scanner to find — `bg-destructive` appears
as a real substring in the compiled file even though it's selected
dynamically at runtime.

### 6.2 Free-text, per-row colors — inline styles, never a dynamic class string

`Member.colorTag` ("cosmetic color used on calendar/kanban/task lists" —
`plan.md` §3.1), `Tag.color`, `Category.color`, and `Event.color` are all
**free-text values a member typed or picked from a color input** — an
open-ended string like `"#7C3AED"`, not one of a fixed set. Tailwind's JIT
compiler only generates CSS for class names it can find as literal
substrings in your source files; it cannot see or generate a class for a
value interpolated at request time. This is not a style preference, it's
why the naive version silently renders unstyled:

```tsx
// ❌ Wrong — Tailwind's compiler never sees `bg-[#7C3AED]` as a class name
// in source (it only sees the template literal), so this class is never
// generated and the element renders with no background at all.
<span className={`bg-[${member.colorTag}]`}>{member.displayName}</span>
```

```tsx
// ✅ Right — inline style for any DB-sourced, open-ended color value.
// src/modules/tasks/components/assignee-dot.tsx
export function AssigneeDot({ member }: { member: { displayName: string; colorTag: string | null } }) {
  return (
    <span
      className="inline-block h-2.5 w-2.5 rounded-full ring-1 ring-border"
      style={{ backgroundColor: member.colorTag ?? "var(--muted-foreground)" }}
      aria-hidden="true"
    />
  );
}
```

The same rule applies everywhere a module renders a `Tag`, `Category`, or
`Event.color` value — `style={{ backgroundColor: tag.color ?? undefined }}`,
never a templated class name. `KanbanColumn` and calendar `Event` chips
follow the identical pattern for `Event.color`.

## 7. Anatomy of a module component

The fullest worked example already committed is `docs/resources.md`
§2.7–2.9's `Contact` list/detail/form trio (`ContactList`, `ContactRow`,
`ContactDetail`, `ContactForm`, `NewContactDialog`) — read that before
building the next entity's UI; the shape below only restates the rules
that example follows, so the next module's components don't have to
rediscover them.

### 7.1 Server vs. Client components

- A page (`src/app/(app)/<route>/page.tsx`) is always a Server
  Component: it resolves the member via `requireMember()`
  (`docs/project-structure.md` §6), calls exactly one query, and renders
  one module component.
- A module component is a Server Component **by default** — only add
  `"use client"` when it actually needs interactivity: local state
  (`ContactDetail`'s `editing` toggle), a hook (`useTransition`,
  `useForm`), or a browser-only API (drag-and-drop in Kanban). A purely
  presentational card with no click handlers of its own stays a Server
  Component and never needs the directive.
- Interactive leaf components (a `<Switch>` toggle, a delete button) can be
  pulled out as small `"use client"` islands inside an otherwise-server
  page instead of marking the whole page/tree client — prefer the smallest
  client boundary that satisfies the need.

### 7.2 File and export naming

kebab-case filename, PascalCase named export, one component's primary
export per file (helper sub-components like `ContactRow` inside
`contact-list.tsx` are fine to colocate when they're only ever used by
the file's main export):

```
src/modules/tasks/components/
├── task-list.tsx        → export function TaskList(...)
├── task-card.tsx         → export function TaskCard(...)
├── task-form.tsx         → export function TaskForm(...)
└── task-form.test.tsx
```

### 7.3 Composing from primitives, never re-deriving them

```tsx
// src/modules/finance/components/budget-progress.tsx
import { Card, CardHeader, CardTitle, CardContent } from "@/components/ui/card";
import { Progress } from "@/components/ui/progress";
import { cn } from "@/lib/utils";
import type { Budget } from "@prisma/client";

export function BudgetProgress({ budget, amountSpent }: { budget: Budget; amountSpent: number }) {
  const percentUsed = Math.round((amountSpent / Number(budget.amount)) * 100);
  const isOverThreshold = percentUsed >= budget.alertThresholdPercent;

  return (
    <Card>
      <CardHeader>
        <CardTitle className="text-base font-medium">{budget.period} budget</CardTitle>
      </CardHeader>
      <CardContent className="space-y-2">
        <Progress
          value={Math.min(percentUsed, 100)}
          className={cn(isOverThreshold && "[&>div]:bg-destructive")}
        />
        <p className="text-sm text-muted-foreground">
          {percentUsed}% used {isOverThreshold && "— approaching limit"}
        </p>
      </CardContent>
    </Card>
  );
}
```

Nothing here reaches for a raw `<div>` where `Card`/`Progress` already
exist — a new module component composes `src/components/ui/*` the way this
one does, exactly like `docs/resources.md`'s `ContactForm` composes
`Input`/`Select`/`Switch`/`Form*` rather than hand-rolling form controls.

## 8. Cross-module composites

`src/components/` (no `/ui`) holds pieces every module's pages use but that
carry no entity-specific meaning of their own:

```tsx
// src/components/empty-state.tsx
import type { ReactNode } from "react";

export function EmptyState({ title, description, action }: { title: string; description?: string; action?: ReactNode }) {
  return (
    <div className="flex flex-col items-center justify-center gap-2 rounded-lg border border-dashed p-10 text-center">
      <p className="font-medium">{title}</p>
      {description && <p className="text-sm text-muted-foreground">{description}</p>}
      {action}
    </div>
  );
}
```

```tsx
// used identically from unrelated modules — no import of each other
// src/modules/notes/components/note-list.tsx
{notes.length === 0 && <EmptyState title="No notes yet" description="Capture your first note." action={<NewNoteDialog />} />}

// src/modules/life-admin/components/renewal-list.tsx
{renewals.length === 0 && <EmptyState title="No renewals tracked" description="Add a warranty, lease, or subscription." action={<NewRenewalDialog />} />}
```

`app-shell/nav.tsx` and `app-shell/command-palette.tsx` are the other
notable residents here — per `docs/project-structure.md` §4.3, they render
purely from `ModuleSurfaceRegistration` rows (`navigation_item`,
`command_palette_action`) via the static `surfaces.ts` map, never from a
hardcoded per-module `if` branch. A 9th module's nav entry is a data row,
not a change to `nav.tsx`'s own code.

## 9. Forms inside components

Full Server-Action-wiring conventions belong in `docs/forms.md` (a harness
gap as of this writing) — this doc only covers the shadcn primitive
composition, which is already established by `docs/resources.md`'s
`ContactForm`:

- `react-hook-form`'s `useForm` + `zodResolver`, resolving against the
  module's own `entities/<name>.ts` input schema (e.g.
  `contactInputSchema`) — never a form-local, hand-written validation
  schema that drifts from the one the Server Action itself validates
  against.
- shadcn's `Form`/`FormField`/`FormItem`/`FormLabel`/`FormControl`/
  `FormMessage` wrapper components, not raw `<label>`/error-`<span>`
  markup — they wire ARIA `aria-invalid`/`aria-describedby` automatically
  from `react-hook-form`'s field state.
- A "new X" flow is a shadcn `Dialog` (`NewContactDialog`), not a
  dedicated `/new` route, per the plan's "fast to add things, quick
  capture, low friction" principle (`plan.md` §1) — reserve a full route
  for a detail/edit view, not for creation.
- Edit-in-place (`ContactDetail`'s `editing` state swapping the same
  `ContactForm` in) is the default pattern for "edit an existing record" —
  don't add a separate `/edit` route unless the entity's edit form is
  genuinely too large for a dialog/inline swap (e.g. a full `Transaction`
  with splits).

## 10. Responsive & mobile conventions

`plan.md` §1: Home OS is "a responsive web application, used the same way
on desktop and mobile browsers (no separate native app)." Concretely:

- Mobile-first utility ordering — write the unprefixed (mobile) class
  first, add `sm:`/`md:`/`lg:` overrides for wider viewports, matching
  `docs/resources.md`'s own `grid gap-2 sm:grid-cols-2 lg:grid-cols-3`.
- `KanbanBoard`'s columns scroll horizontally on narrow viewports rather
  than stacking or hiding — `overflow-x-auto` on the board container, each
  `KanbanColumn` a fixed min-width flex child, so drag-and-drop still works
  the same way on a phone as on desktop (no separate mobile Kanban layout).
- Calendar's month/week/day views (`plan.md` §3.2) collapse to day view as
  the default on narrow viewports — this is a data/query concern
  (`getEventsInRange` still returns the same shape) with a responsive
  `components/{month-view,week-view,day-view}.tsx` picking which one
  renders by viewport, not three unrelated implementations.
- Tap targets on `ShoppingListItem` checkboxes and swipe/long-press
  affordances anywhere touch-first interaction matters use shadcn's
  default `Checkbox`/`Switch` sizing (already ≥24px) — don't shrink an
  interactive control below that to fit more rows on screen.
- No horizontal page scroll, ever: any inherently wide element (a Finance
  `Table` of transactions, a wide calendar week view) gets its own
  `overflow-x-auto` wrapper, never lets the whole page scroll sideways.

## 11. Accessibility

Radix UI — the primitive layer under every shadcn component in this repo — already
provides correct roles, keyboard navigation, and focus trapping for
`Dialog`, `Select`, `DropdownMenu`, `Switch`, etc. What a module's own
component code is still responsible for:

- **`aria-label` on icon-only buttons.** `docs/resources.md`'s
  `contact-list.tsx` pin/unpin button is the model to copy: `aria-label={
  contact.isPinned ? "Unpin contact" : "Pin contact"}` — any icon-only
  `Button` (delete, snooze, mark-complete) needs the equivalent.
- **Focus-visible rings use the token, not a hardcoded color** — shadcn's
  `Button`/`Input` already apply `focus-visible:ring-ring`; don't override
  that with a literal color when customizing a primitive (§4.2).
- **Never encode state by color alone.** A `Renewal` in `expired` status,
  an overdue `Task`, a budget past its `alertThresholdPercent` — each also
  gets a text label or icon (`docs/resources.md`'s badge/label pattern),
  not just a red background, since `colorTag`/category colors (§6.2) are
  member-chosen and can't be relied on for contrast or color-blind
  legibility.
- **Client-side conditional rendering of an action is UX only, never the
  security boundary** — `ContactDetail`'s delete button hiding when
  `contact.createdBy !== currentMemberId` is exactly this: a courtesy, not
  enforcement. The real gate is the Server Action's `requireRole()`/
  ownership check (`docs/access-control.md`) — a component never assumes
  hiding a button is sufficient.

## 12. Testing components

Full runner/fixture conventions belong in `docs/testing.md` (a harness gap
as of this writing). What's already established, per `CLAUDE.md` rule 4 and
`docs/resources.md` §2.10's pattern:

- Colocated `<component>.test.tsx` next to the component
  (`task-form.tsx` → `task-form.test.tsx`), not a separate `__tests__/` tree.
- Component tests use React Testing Library queries by role/label text
  (`getByRole("button", { name: "Add contact" })`), not snapshot tests or
  querying by CSS class/Tailwind utility — a Tailwind class renaming during
  a design tweak must never break a test.
- A form component's test asserts the accessible error path (submitting
  with an invalid value surfaces the `FormMessage` text), not just that the
  happy path renders.

## 13. Why no Storybook in V1

Recorded as a deliberate decision in `README.md`'s tech-stack table and
`ROADMAP.md`'s "Tooling decisions" section — restated here since this is
the doc someone opens specifically to ask "should this component get a
story":

- shadcn/ui's primitives are already consistent and self-documenting by
  construction — every `Button`/`Dialog`/`Select` in the app is the exact
  same file, so there's no divergent variant surface across modules that a
  living style guide would need to reconcile.
- Home OS has, as of this harness, **zero bespoke design-system components**
  beyond what's copied in from shadcn and the thin composites in §8 — there
  is no component library substantial enough to justify a second build
  tool and a second place to keep in sync with real usage.
- The bar to revisit: if a genuinely large, bespoke component library
  emerges beyond shadcn/ui basics (per `ROADMAP.md`'s own wording), Storybook
  becomes worth adding — that's a call for whoever's driving that future
  work to make explicitly (updating `ROADMAP.md`'s tooling-decisions note
  and this section together), not something to add preemptively "just in
  case" on the next module.

## 14. Checklist: adding a new UI component

1. Confirm it isn't already covered (§3) — an existing primitive, an
   existing composite, or a sibling module's near-identical component.
2. Place it in the correct tier (§2): `src/components/ui/` only via the
   shadcn CLI (§4); `src/components/` for domain-agnostic composites;
   `src/modules/<key>/components/` (or `src/lib/<domain>/components/` for
   platform entities) for anything with entity meaning.
3. Server Component by default; add `"use client"` only for the smallest
   subtree that actually needs interactivity (§7.1).
4. Compose from `src/components/ui/*` — never hand-roll markup a primitive
   already provides.
5. Any color sourced from the database (`Member.colorTag`, `Tag.color`,
   `Category.color`, `Event.color`) is an inline `style`, never a
   templated Tailwind class (§6.2); any color keyed off a fixed enum is a
   literal class-string lookup map (§6.1).
6. `cn()` for conditional classes (§5.3) — never manual string
   concatenation.
7. Icon-only interactive elements get `aria-label` (§11).
8. A form composes shadcn's `Form`/`FormField` family against the module's
   own `zod` input schema (§9), not a hand-rolled validation path.
9. Colocated `*.test.tsx` asserting the accessible happy path and at least
   one error/edge state (§12).
10. `pnpm lint && pnpm typecheck && pnpm test && pnpm build` before calling
    it done, per `CLAUDE.md`'s verification rule.

## 15. Success/error feedback (toasts)

Sonner's `<Toaster />` is mounted once, in the root `src/app/layout.tsx` —
never mount a second one. `import { toast } from "sonner"` anywhere a
mutation needs to report its result; there is no wrapper component for the
call itself, only for the three mechanisms below.

**Wording convention:** past-tense, `"{Entity} {verb}"`, no exclamation
mark, Title-case entity name matching that module's own UI copy.
`"{Entity} created"`/`"{Entity} updated"` are the *generic* defaults, used
only for a plain form save with no more specific verb available — an action
that transitions an entity to a specific named state always uses that verb
instead (`"Subscription paused"`, never `"Subscription updated"`). This
codebase spells it **"cancelled"** (double-L, matching the
`RenewalStatus`/`SubscriptionStatus` enum values themselves), not
"canceled".

**Three mechanisms, by call-site shape — don't invent a fourth:**

- **A form's own `onSubmit`** (§9): every `*-form.tsx` already has an
  identical `try { await createX/updateX(...); onDone(); } catch { form.setError("root", ...) }`
  shape. Add `toast.success(...)` right after the mutation resolves, before
  `onDone()` — inside the form itself, not at each dialog/list call site
  that renders it, so every current and future caller gets it for free.
- **A destructive confirmation** — always the shared `ConfirmDialog`
  (`src/components/confirm-dialog.tsx`), never a hand-rolled `AlertDialog`
  (a real bug was found and fixed where two components did exactly that,
  with zero error handling at all). Pass `successMessage`; omit it only
  when `onConfirm` itself navigates away or ends the session (e.g.
  `closeHousehold()` + `logout()`) — a toast that can't render, or renders
  on an unrelated page, is worse than no toast.
- **A fire-and-forget button** with no form and no confirmation (a
  checkbox, an archive/pause/resume button) — `useActionFeedback()`
  (`src/hooks/use-action-feedback.ts`). Replace
  `startTransition(async () => { await someAction(...) })` with
  `run(() => someAction(...), "optional success message")`. Omit the
  message for a toggle clicked repeatedly in quick succession (a checkbox,
  a pause/resume switch) — a toast on every click is noise, not signal; the
  error path still always fires. **Do not use this hook** for an action that
  returns an `ActionResult` (`{success, error}`) instead of throwing — the
  hook assumes throw-on-failure and would silently treat a logical failure
  as success. Those sites (there are a couple, e.g. `changeMemberRole()`)
  add the toast manually in their existing `if (!result.success) ... else toast.success(...)` branch instead.
