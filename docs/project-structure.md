# Project Structure

This document is the detailed reference for **where code lives** in Home OS
and **the mechanical steps to add to it** — folder layout, naming, and the
one rule that makes the platform extensible: a module is a set of files in a
predictable shape plus a handful of registration rows, never a special case
wired by hand into another module's code.

Related docs, each covering a different angle of the same system:
- `AGENTS.md` — the short-form version of this file plus the new-module
  checklist, for quick orientation.
- `docs/module-architecture.md` — the full data contract for `Module` /
  `ModuleEventType` / `EventSubscription` / `ModulePermissionDeclaration` /
  `ModuleGrant` / `ModuleSurfaceRegistration` (required fields, health-status
  transitions, grant review UX, event contract versioning). This file only
  covers *where the code for that system lives* and *what file you touch to
  add to it*.
- `docs/orm-conventions.md` — Prisma-level conventions (naming, enums, soft
  delete, migration naming) for the single `prisma/schema.prisma` file
  whose location this doc explains.
- `docs/access-control.md`, `docs/email.md`,
  `docs/auth.md`, `docs/forms.md`, `docs/ui-components.md`, `docs/testing.md`,
  `docs/verify.md` — conventions for specific concerns that cut across every
  module folder described below.

If a doc referenced above doesn't exist yet in this checkout, that's a gap
in the harness, not permission to invent a different structure — follow this
file and `CLAUDE.md`'s non-negotiable rules until the gap is filled.

---

## 1. The mental model: three layers, one direction of dependency

Every file in `src/` belongs to exactly one of three layers. Understanding
which layer a file is in tells you what it's allowed to import.

```
src/app/        ← routing only (Next.js App Router pages, layouts, Route Handlers)
      │           imports from src/modules/* and src/lib/*, never the reverse
      ▼
src/modules/    ← the 8 product modules from plan.md: dashboard, tasks, kanban,
                  calendar, reminders, notes, finance, life-admin
      │           each imports src/lib/* freely, and may import another
      │           module's public barrel (src/modules/<other>) — never its
      │           internals
      ▼
src/lib/        ← the platform substrate: Prisma client, auth/session,
                  Household & Sharing, the Module/Event registry, the event
                  bus, Resend/email. Imports nothing from src/modules or
                  src/app — the substrate never depends on what's built on it.
```

**Household, Member, Invite, ObjectShare, NotificationPreference,
DigestSubscription, and Notification are not one of "the 8 modules."** They
are platform substrate every module depends on (multi-tenancy root, the
`visibility`/`ObjectShare` contract, the notification/email plumbing), so
they live under `src/lib/`, not `src/modules/`. They don't get a `Module`
row, a health status, or a `ModuleGrant` — they're what the `Module`/
`ModuleGrant` system itself runs on top of. Same reasoning for `Module`,
`ModuleEventType`, `EventSubscription`, `EventOccurrence`,
`ModulePermissionDeclaration`, `ModuleGrant`, `ModuleSurfaceRegistration`
themselves — the registry can't be a member of the thing it's registering.

The 8 modules in `src/modules/` **are** pluggable in principle — each has a
`Module` row, a `healthStatus`, and can (in the case of a 9th/custom module)
require review before a household grants it access. That pluggability is
exactly why their code is kept in one predictable per-module shape (§3) and
never reached into directly from outside (§7).

## 3. Anatomy of a module folder

Every folder under `src/modules/<key>/` follows the same shape. Not every
module needs every subfolder (Dashboard has no `entities/`, since it owns no
data — see §3.1) but none of them invent a subfolder the others don't have.

| Folder | Purpose |
|---|---|
| `entities/` | Zod input/output schemas and small pure functions derived from the module's Prisma models — **not** the Prisma models themselves (those live in the one `prisma/schema.prisma`, §5). E.g. `createTaskInputSchema`, `getTaskStatus()`. |
| `actions/` | Server Actions (`"use server"`) — the only way UI triggers a mutation. One file per action, colocated `.test.ts` next to it. |
| `queries/` | Server-side read functions called from Server Components and from other modules' `queries/`. Always take `householdId` explicitly (see `CLAUDE.md` rule 1). |
| `components/` | React components specific to this module's domain. Composed from `src/components/ui/` primitives. Colocated `.test.tsx` next to the component under test. |
| `events/` | `emitters.ts` (wraps `emitEvent` for this module's `ModuleEventType` keys) and/or `subscribers.ts` (this module's reactions to events owned by other modules). |
| `jobs/` | Functions invoked by a `src/app/api/cron/*/route.ts` handler — scheduled sweeps, never called from UI. |
| `module.ts` | This module's self-description — see §9. The only file every module has that isn't optional. |
| `index.ts` | The module's public barrel — the only import path other modules are allowed to use (§7). |

Tests are **colocated**, not collected into a separate `tests/` folder —
`src/modules/tasks/actions/complete-task.ts` sits next to
`complete-task.test.ts`. See `docs/testing.md` for what counts as adequate
coverage; cross-module flows go in `e2e/` instead (Playwright).

### 3.1 A module with no data of its own: `dashboard`

`dashboard` owns zero Prisma models — it's a query/aggregation layer over
what every other module already stores, plus the quick-capture and
search/palette surfaces. Its folder has no `entities/`, `actions/`, `jobs/`,
or `events/`; only `queries/`, `components/`, `module.ts`, `index.ts`.

```ts
// src/modules/dashboard/queries/get-today.ts
import { getOverdueAndDueTasks } from "@/modules/tasks";
import { getEventsInRange } from "@/modules/calendar";
import { getUpcomingSubscriptions } from "@/modules/finance";
import { getActiveReminderOccurrences } from "@/modules/reminders";
import { startOfHouseholdDay, endOfHouseholdDay } from "@/lib/dates";

export async function getToday(householdId: string, memberId: string, timezone: string) {
  const from = startOfHouseholdDay(timezone);
  const to = endOfHouseholdDay(timezone);

  const [tasksDue, eventsToday, upcomingBills, activeReminders] = await Promise.all([
    getOverdueAndDueTasks(householdId, memberId, to),
    getEventsInRange(householdId, from, to),
    getUpcomingSubscriptions(householdId, { withinDays: 7 }), // fixed 7-day lookahead, not per-member
    getActiveReminderOccurrences(householdId, memberId),
  ]);

  return { tasksDue, eventsToday, upcomingBills, activeReminders };
}
```

Every function Dashboard calls is imported from another module's `index.ts`
barrel — it never reaches into `@/modules/tasks/queries/*` directly (§7),
and it never queries `prisma.task` itself. That's what makes "Dashboard
code needs zero changes when a 9th module registers a search provider" true
for search/palette (`ModuleSurfaceRegistration`, §9) while `getToday()`
above still needs one new import + one new `Promise.all` entry if a 9th
module wants a "Today" widget slot — the exception is deliberate: `getToday`
composes a fixed, product-designed layout (per plan.md's Dashboard section),
whereas dashboard *widgets*, *search*, and *palette actions* are generic
slots driven entirely by `ModuleSurfaceRegistration` rows (see
`dashboard_widget` in `src/lib/module-registry/surfaces.ts`).

### 3.2 A fully worked module: `tasks`

```ts
// src/modules/tasks/entities/task.ts
import { z } from "zod";

export const taskPrioritySchema = z.enum(["low", "medium", "high", "urgent"]);

export const createTaskInputSchema = z.object({
  title: z.string().min(1).max(200),
  description: z.string().max(5000).optional(),
  dueDate: z.date().optional(),
  dueDateAllDay: z.boolean().default(true),
  priority: taskPrioritySchema.default("medium"),
  assigneeId: z.string().cuid().optional(),
  parentTaskId: z.string().cuid().optional(),
  visibility: z.enum(["private", "household", "specific_members"]).default("household"),
});
export type CreateTaskInput = z.infer<typeof createTaskInputSchema>;

// completedAt is the single source of truth for completion — no separate boolean (plan.md §4)
export function getTaskStatus(task: { completedAt: Date | null; dueDate: Date | null }): "open" | "overdue" | "completed" {
  if (task.completedAt) return "completed";
  if (task.dueDate && task.dueDate < new Date()) return "overdue";
  return "open";
}
```

```ts
// src/modules/tasks/actions/complete-task.ts
"use server";

import { revalidatePath } from "next/cache";
import { prisma } from "@/lib/db";
import { requireMember } from "@/lib/auth/session";
import { emitEvent } from "@/lib/events/emit";

export async function completeTask(taskId: string) {
  const { member, household } = await requireMember();

  const task = await prisma.task.update({
    where: { id: taskId, householdId: household.id }, // both, always — never id alone
    data: { completedAt: new Date(), completedById: member.id },
  });

  await emitEvent(household.id, "task.completed", { taskId: task.id, completedById: member.id }, member.id);

  revalidatePath("/tasks");
  return task;
}
```

```ts
// src/modules/tasks/events/emitters.ts
import { emitEvent } from "@/lib/events/emit";

export async function emitTaskAssigned(householdId: string, taskId: string, assigneeId: string, byMemberId: string) {
  return emitEvent(householdId, "task.assigned", { taskId, assigneeId }, byMemberId);
}
```

```ts
// src/modules/tasks/index.ts — the public barrel: the ONLY import path other modules use
export { getOverdueAndDueTasks, getTasksDueInRange } from "./queries/get-overdue-tasks";
export { getTask } from "./queries/get-task";
export { createTask } from "./actions/create-task";
export { completeTask } from "./actions/complete-task";
export type { CreateTaskInput } from "./entities/task";
// NOT exported: entities/task.ts's internal helpers, actions/*.test.ts, anything else — internal to this module
```

`kanban`'s `move-card.ts` action and `calendar`'s `get-calendar-range.ts`
query both import from `@/modules/tasks` (the barrel above) — never from
`@/modules/tasks/queries/get-task` directly. See §7 for how that's enforced.

### 3.3 A module that's also a shared capability: `reminders`

Per plan.md, "any other module creates Reminders through this shared
capability rather than building its own alerting." Concretely: `finance`,
`life-admin`, and `dashboard`'s quick-capture all import
`createReminder()` straight from `@/modules/reminders`'s barrel — a normal
same-module-system import, no event needed, because the caller wants the
Reminder created *now*, synchronously, as part of its own transaction:

```ts
// src/modules/life-admin/actions/create-renewal.ts (excerpt)
"use server";
import { createReminder } from "@/modules/reminders";

// ... after prisma.renewal.create(...):
for (const offsetDays of renewal.reminderOffsetsDays) {
  await createReminder({
    householdId: renewal.householdId,
    title: renewal.title, // snapshot — Reminder.title is not synced to source renames
    targetMemberId: renewal.responsibleMemberId,
    sourceType: "renewal",
    sourceModule: "life_admin",
    sourceEntityId: renewal.id,
    firstRemindAt: subDays(renewal.expiryDate, offsetDays),
  });
}
```

This is a direct dependency (`life-admin`'s `module.ts` declares
`dependsOnModules: ["reminders"]`), not a pub/sub reaction — same pattern as
`kanban`'s `move-card` action, which calls `completeTask()` directly from
`@/modules/tasks` (kanban's own manifest already declares `dependsOnModules:
["tasks"]`) when a card lands in a done-typed column, rather than reacting
to a `task.completed` `EventSubscription`. None of the 8 built-in modules
subscribe to each other's events in V1 — every one of their cross-module
reactions is a direct, permission-checked function call through the barrel,
not a fan-out through `EventSubscription`/`EventOccurrence`. Use a direct
barrel import when the caller needs the result synchronously or the
dependency is structural — which covers every built-in-to-built-in reaction
today; use an event subscription only for a 9th/custom module's genuinely
optional reaction to another module's events, where the two modules
shouldn't need to know about each other (see `docs/module-architecture.md`
for the full contract, and `docs/seeding.md` §5.4 for why no
`EventSubscription` rows are seeded for the 8 built-ins).

## 4. The platform layer (`src/lib/`) in detail

This is the "shared platform layer, not inside any one module" the
extensibility system needs. Nothing under `src/lib/` imports from
`src/modules/` or `src/app/`.

### 4.1 `src/lib/household/` — multi-tenancy & sharing

`Household`, `Member`, `Invite`, `ObjectShare`. Exposes `visibility.ts`'s
`withVisibility()` helper, which every module's `queries/` file calls — see
the worked example in `CLAUDE.md` rule 2
(`src/modules/tasks/queries/get-visible-tasks.ts`). The generic
deletion-cleanup that removes stale `ObjectShare` rows when a shareable
entity is deleted also lives here (`src/lib/household/actions/` — a single
infra-level hook, not one per module).

### 4.2 `src/lib/events/` — the event bus runtime

```ts
// src/lib/events/emit.ts
import { prisma } from "@/lib/db";
import { dispatchToSubscribers } from "./dispatch";

export async function emitEvent(
  householdId: string,
  eventTypeKey: string, // e.g. "task.completed"
  payload: Record<string, unknown>,
  triggeredByMemberId: string,
) {
  const eventType = await prisma.moduleEventType.findUniqueOrThrow({ where: { key: eventTypeKey } });

  const occurrence = await prisma.eventOccurrence.create({
    data: {
      householdId,
      eventTypeId: eventType.id,
      emittedByModule: eventType.owningModule,
      occurredAt: new Date(),
      triggeredByMemberId,
      payloadSnapshot: payload,
    },
  });

  await dispatchToSubscribers(occurrence); // fans out to active EventSubscription rows
  return occurrence;
}
```

`dispatch.ts` also unconditionally creates a `Notification` row (subject to
`NotificationPreference`) for the occurrence's `categoryKey` when that
category isn't already backed by a `Reminder` — this is baseline platform
behavior, not something a module opts into by registering an
`EventSubscription`. `EventSubscription` rows are for a 9th/custom module's
genuine reactions to another module's events — none of the 8 built-ins
subscribe to each other's events in V1 (§3.3, `docs/seeding.md` §5.4) — not
for the Notification/email fan-out every event gets for free.

### 4.3 `src/lib/module-registry/` — the extensibility registry

Named `module-registry`, deliberately **not** `modules`, so it's never
confused with `src/modules/` (the product modules it catalogs). Holds
`Module`, `ModuleEventType`, `EventSubscription`, `EventOccurrence`,
`ModulePermissionDeclaration`, `ModuleGrant`, `ModuleSurfaceRegistration` —
the query/action code around them, and `registry.ts`, which is the one file
every new module's manifest gets appended to (§9).

`surfaces.ts` is worth calling out: `ModuleSurfaceRegistration.target` is
just a string column in Postgres (e.g. `"tasks.create"`,
`/modules/tasks/widgets/due-today"`). Next.js can't dynamically `import()` a
component from a runtime database string in a serverless deployment, so
`surfaces.ts` is a small static TypeScript map from those target strings to
the actual imported function/component reference, built once at compile
time from every module's manifest:

```ts
// src/lib/module-registry/surfaces.ts (excerpt)
import { createTask } from "@/modules/tasks";
import { createNote } from "@/modules/notes";
import { createReminder } from "@/modules/reminders";

export const quickCaptureTargets = {
  "tasks.create": createTask,
  "notes.create": createNote,
  "reminders.create": createReminder,
} as const;
```

This is the one other place (besides `registry.ts` itself) a brand-new
module's quick-capture/search/palette entry gets a line — see §9 step 4.
It's still registration, not special-casing: every module gets exactly one
entry in the same flat map, none of them behind an `if (moduleKey === ...)`.

### 4.4 `src/lib/notifications/` and `src/lib/email/`

`NotificationPreference`, `DigestSubscription`, `Notification` on one side;
the Resend client and React-Email templates on the other.
`src/lib/notifications/jobs/send-digests.ts` is what
`src/app/api/cron/digests-send/route.ts` calls.

## 5. Prisma schema & migrations

**One file:** `prisma/schema.prisma`. This repo does not use Prisma's
multi-file schema (`prismaSchemaFolder`) — a single file keeps every
relation trivially visible in one place, which matters more here than the
convenience of per-module files, given how many models reference each other
across module boundaries (`Task.assigneeId → Member`, `Transaction.attachment
→ Document`, `NoteTag.tagId → Tag`, etc.). The file is organized into
banner-commented sections, one per owning module, in the same order as
`src/modules/`:

```prisma
// prisma/schema.prisma (structure — see docs/orm-conventions.md for full field lists)

// ============================================================
// Platform — Household & Sharing (src/lib/household)
// ============================================================
model Household { /* ... */ }
model Member { /* ... */ }
model Invite { /* ... */ }
model ObjectShare { /* ... */ }
model NotificationPreference { /* ... */ }
model DigestSubscription { /* ... */ }
model Notification { /* ... */ }

// ============================================================
// Platform — Module & Event Registry (src/lib/module-registry, src/lib/events)
// ============================================================
model Module { /* ... */ }
model ModuleEventType { /* ... */ }
model EventSubscription { /* ... */ }
model EventOccurrence { /* ... */ }
model ModulePermissionDeclaration { /* ... */ }
model ModuleGrant { /* ... */ }
model ModuleSurfaceRegistration { /* ... */ }

// ============================================================
// Module: tasks (src/modules/tasks)
// ============================================================
model Task { /* ... */ }
model TaskRecurrenceRule { /* ... */ }
model Tag { /* ... */ }        // shared taxonomy — also referenced by notes' NoteTag below
model TaskTag { /* ... */ }

// ============================================================
// Module: kanban (src/modules/kanban)

// ============================================================

// Module: finance (src/modules/finance)
// ============================================================

// ============================================================
// Module: life_admin (src/modules/life-admin)
// ============================================================

model ShoppingListItem { /* ... */ }
```

**The rule:** a change to one module's section never edits another
module's section — with one unavoidable exception. Prisma relations are
declared on both sides, so if a new module's model has a relation *into* an
existing model (like `NoteTag.tagId → Tag`, or `Transaction.attachmentId →
Document`), the referenced model's block needs the matching back-relation
array added (e.g. `Tag` gets a `noteTags NoteTag[]` field). That one-line,
additive, same-shape edit is the only thing a new module is allowed to add
to a section it doesn't own — never a field rename, a new constraint, or
business logic. `docs/orm-conventions.md` has the full naming/enum
conventions; this section only fixes *where* the file lives and *how it's
organized*.

Module folder name vs. `Module.key`/`resourceDomain` value: folder names
under `src/modules/` are kebab-case (`life-admin`) to match Next.js route
segments; `Module.key` and the `resourceDomain` enum values already fixed by
plan.md are snake_case (`life_admin`), because they're literal values other
tables reference. `module.ts`'s `key` field is the one place that
bridges the two — see §9.

Commands:

```bash
pnpm prisma validate                       # schema-only check, no DB round trip
pnpm prisma migrate dev --name add_meal_planning   # generates + applies a migration, regenerates the client
pnpm prisma generate                       # regenerate the client without migrating (e.g. after a git pull)
pnpm prisma db seed                        # runs prisma/seed.ts
```

`prisma/seed.ts` seeds starter `Category` rows and calls
`src/lib/module-registry/registry.ts`'s aggregated manifest list to upsert
every built-in module's `Module` / `ModuleEventType` /
`ModulePermissionDeclaration` / `ModuleSurfaceRegistration` rows, and
pre-seeds their required-declaration `ModuleGrant`s as `granted` for every
household — see §9.

## 6. The routing layer (`src/app/`)

Pages are thin. A page resolves the current member/household (via
`requireMember()`, `src/lib/auth/session.ts`) and calls into a module's
`queries/`; a form posts to a module's `actions/`. No `prisma.*` calls and
no business logic belong in `src/app/`.

```tsx
// src/app/(app)/tasks/page.tsx
import { getVisibleTasks } from "@/modules/tasks";
import { requireMember } from "@/lib/auth/session";
import { TaskList } from "@/modules/tasks/components/task-list";

export default async function TasksPage() {
  const { household, member } = await requireMember();
  const tasks = await getVisibleTasks(household.id, member.id);
  return <TaskList tasks={tasks} />;
}
```

Route groups: `(auth)` for the unauthenticated shell (login, signup, invite
acceptance), `(app)` for everything behind `requireMember()` — one
layout resolving the current household once, reused by every page under it.

`src/app/api/` holds **only** Route Handlers that something outside our own
React tree must call: the five Vercel Cron entries (`vercel.json`) that back
the scheduled jobs described in plan.md's Email Notifications section, plus
`src/app/api/auth/callback/route.ts`, which Supabase's email-confirmation
and password-recovery links hit directly (`docs/auth.md` §4.1) rather than
anything in our own React tree. The five cron handlers are thin: each
verifies the Vercel Cron secret and calls straight into a module's (or
`src/lib/notifications`'s) `jobs/` function — no logic in the route file
itself:

```ts
// src/app/api/cron/reminders-sweep/route.ts
import { sweepDueOccurrences } from "@/modules/reminders/jobs/sweep-due-occurrences";

export async function GET(request: Request) {
  if (request.headers.get("authorization") !== `Bearer ${process.env.CRON_SECRET}`) {
    return new Response("Unauthorized", { status: 401 });
  }
  await sweepDueOccurrences();
  return new Response("ok");
}
```

## 7. Server Actions vs. Route Handlers, and the module-boundary import rule

- **Server Actions** (`actions/*.ts`, `"use server"`) are the default for
  every mutation our own UI triggers — forms, buttons, drag-and-drop drops.
- **Route Handlers** (`src/app/api/**/route.ts`) exist for the cron sweeps
  above, plus exactly one more: `src/app/api/auth/callback/route.ts`, which
  Supabase's email-confirmation and password-recovery links hit directly
  (`docs/auth.md` §4.1) — a `GET` handler is the only way to receive that
  emailed link's `token_hash`/`type` query params, so it can't be a Server
  Action. Outside those six handlers there is no product reason to add
  another one; if a task seems to need one, re-check whether it should be
  a Server Action instead.
- **Cross-module imports go through `index.ts` only.** `src/modules/kanban`
  may `import { completeTask } from "@/modules/tasks"`; it may not
  `import { getTaskStatus } from "@/modules/tasks/entities/task"`. This is
  **convention, not yet ESLint-enforced** — `eslint.config.mjs` doesn't
  currently have a `no-restricted-imports` rule at all (verified directly,
  during Dashboard's build — every module built so far followed this rule
  by discipline, which is why the gap went unnoticed for seven modules).
  The rule this doc originally sketched would need real per-file-glob
  scoping to not immediately break the codebase — `src/app/**` and
  `src/components/**` legitimately reach into `@/modules/*/components/*`
  directly (docs/resources.md §2.7's documented exception, used by every
  module's own pages), so a correct version needs `files`/`ignores` scoping
  in ESLint's flat config, not the single blanket pattern shown in an
  earlier draft of this doc. Tracked as a known harness gap
  (`ROADMAP.md`'s "Known harness gaps" section) rather than implemented
  half-right under time pressure.
- **A stricter, *already-proven* rule for one specific case: a `"use
  client"` component must import a Server Action straight from that
  action's own file — never through any barrel that also re-exports a
  sibling with a heavier transitive dependency.** This isn't
  aspirational — it broke a real `pnpm build` during Dashboard's own work.
  `src/components/app-shell/command-palette.tsx` needs
  `@/modules/dashboard`'s `search()` (a `"use server"` action); that
  barrel's `index.ts` *also* re-exports `searchEverything` (a plain
  function, not `"use server"`), which imports Life Admin's
  `getVisibleContacts` — and Life Admin's own barrel, in that same file,
  exports `getDocumentDownloadUrl`, which needs `@/lib/supabase/admin`'s
  `"server-only"` admin client. Webpack resolves a barrel's re-export
  statements as one unit when building a client bundle — importing
  anything from a barrel pulls in every sibling export's transitive chain,
  not just the one name actually used. Next.js's `"use server"`
  file-level transform only reliably protects the client bundle when the
  client component imports straight from the file that has `"use server"`
  at its top:

  ```tsx
  // ✗ breaks the client build the moment any sibling barrel export has a
  //   server-only transitive dependency, even one this file never uses
  import { search } from "@/modules/dashboard";

  // ✓ imports the "use server" file directly — Next's compiler swaps in a
  //   lightweight RPC stub for the client bundle, the real implementation
  //   (and its dependency chain) only ever lands in the server bundle
  import { search } from "@/modules/dashboard/actions/search-action";
  ```

  A module's own files still use relative imports internally
  (`../entities/task`), which none of the above touches — this is only
  about imports crossing a module boundary from outside.

## 8. Shared, reusable UI

- `src/components/ui/` — shadcn/ui primitives, added with the CLI and
  committed (not installed as a package): `pnpm dlx shadcn@latest add button
  dialog table dropdown-menu`. One `Button`, one `Table`, one `Dialog` for
  the whole app — see `docs/ui-components.md`.
- `src/components/` (no `/ui`) — composite components with no domain
  meaning of their own: `app-shell/nav.tsx` (renders nav from
  `ModuleSurfaceRegistration` `navigation_item` rows), `page-header.tsx`,
  `empty-state.tsx`, `confirm-dialog.tsx`.
- Anything tied to a specific entity (even a platform one, like
  `notification-bell.tsx`) lives with that entity's owning layer
  (`src/lib/notifications/components/`), not in generic `src/components/`.
- No Storybook in V1 (locked decision, see `README.md` and
  `docs/ui-components.md`) — shadcn/ui's own components are the
  documentation.

## 9. Adding a 9th module — the registration checklist

This is "registration, not special-casing" made concrete. Every step below
is additive to a shared list or a brand-new folder; none of them is a
conditional branch on which module you're adding.

1. **Scaffold the folder.**
   ```bash
   pnpm run scaffold:module -- meal-planning
   ```
   `scripts/scaffold-module.mjs` creates
   `src/modules/meal-planning/{entities,actions,queries,components}/`, a
   stub `module.ts`, and a stub `index.ts` — the same shape as
   every module in §2, nothing custom.

2. **Add its Prisma models.** Append a new banner section at the bottom of
   `prisma/schema.prisma` (§5) — `model MealPlan { ... }`,
   `model MealPlanItem { ... }`. If a model relates into an existing one
   (e.g. it reuses `Tag`), add the one-line back-relation array to that
   model per the exception rule in §5. Then:
   ```bash
   pnpm prisma migrate dev --name add_meal_planning
   ```

3. **Fill in `module.ts`.**
   ```ts
   // src/modules/meal-planning/module.ts
   import type { ModuleManifest } from "@/lib/module-registry/types";

   export const mealPlanningManifest: ModuleManifest = {
     key: "meal_planning",
     name: "Meal Planning",
     description: "Plan weekly meals and generate a shopping list from them.",
     version: "1.0.0",
     kind: "custom",
     dependsOnModules: ["life_admin"], // reuses ShoppingList/ShoppingListItem
     eventTypes: [
       { key: "meal_plan.published", label: "Meal plan published", payloadSummary: "{ mealPlanId, weekOf }", contractVersion: 1, relatedEntityType: "MealPlan" },
     ],
     permissionDeclarations: [
       { resourceDomain: "life_admin", accessLevel: "write", purpose: "Create ShoppingListItems from planned meals", isRequired: true },
       { resourceDomain: "cross_module_events", accessLevel: "write", purpose: "Emit meal_plan.* events", isRequired: true },
     ],
     surfaceRegistrations: [
       { surface: "navigation_item", label: "Meal Planning", icon: "UtensilsCrossed", target: "/meal-planning", sortOrder: 70 },
       { surface: "quick_capture_target", label: "Meal plan", target: "meal_planning.create", sortOrder: 60 },
       { surface: "global_search_provider", label: "Meal plans", target: "meal_planning.search", sortOrder: 60 },
     ],
   };
   ```

4. **Register it in exactly two shared files** — the only files outside the
   module's own folder that get touched:
   ```ts
   // src/lib/module-registry/registry.ts
   import { mealPlanningManifest } from "@/modules/meal-planning/module";
   // ...
   export const moduleManifests = [
     dashboardManifest, tasksManifest, kanbanManifest, calendarManifest,
     remindersManifest, notesManifest, financeManifest, lifeAdminManifest,
     mealPlanningManifest, // ← the one line every new module adds
   ];
   ```
   ```ts
   // src/lib/module-registry/surfaces.ts — only if it registered a quick_capture_target
   import { createMealPlan } from "@/modules/meal-planning";
   export const quickCaptureTargets = {
     // ...
     "meal_planning.create": createMealPlan,
   } as const;
   ```

5. **Implement the module** — `entities/`, `actions/`, `queries/`,
   `components/`, `events/` and/or `jobs/` as needed, each with colocated
   tests, exactly like §3.2's `tasks` example. Export only the intended
   public surface from `index.ts`.

6. **Seed the registry rows.**
   ```bash
   pnpm prisma db seed
   ```
   This upserts the new `Module`, `ModuleEventType`,
   `ModulePermissionDeclaration`, and `ModuleSurfaceRegistration` rows from
   `moduleManifests`. Because `kind: "custom"`, **no `ModuleGrant` is
   pre-seeded** — every household sees it as `pending_review` under
   Settings → Modules until an owner/admin explicitly grants it (the one
   end-user-facing part of this system, `src/app/(app)/settings/modules/page.tsx`).
   A `kind: "built_in"` addition (only the Home OS team itself would ship
   one) *does* get its required declarations pre-seeded as `granted` for
   every household, same as the original 8.

7. **Nothing else changes.** No edit to
   `src/modules/dashboard/`, `src/app/(app)/layout.tsx`'s nav
   rendering, or any other module's code. If a change you're making to add
   a module requires touching a file outside steps 1–6, that's a sign
   you're special-casing rather than registering — stop and re-read
   `docs/module-architecture.md`.

**Anti-pattern to reject in review:** any `if (moduleKey === "tasks")` /
`switch (module.key)` branch inside `src/lib/module-registry/`,
`src/modules/dashboard/`, or `src/components/app-shell/` — the whole point
of the manifest + registry + surfaces map is that every module, built-in or
9th-and-beyond, goes through the same flat list and the same lookup.
